# Part 1 — Foundation

---

# 1. Purpose

The Engineering Competency Framework defines the abilities Project Blacksmith develops throughout the learning journey.

Unlike traditional programming roadmaps, which organize learning around language features, Blacksmith organizes learning around engineering capability.

Programming languages, frameworks, libraries, and tools are implementation mediums.

Competencies are permanent.

Every mission, review, interview, and project exists to improve one or more competencies.

This framework becomes the authoritative reference for measuring engineering growth.

---

# 2. Philosophy

The objective of Blacksmith is not to produce JavaScript developers.

The objective is to produce software engineers who can rapidly adapt to new technologies.

Learning JavaScript is therefore treated as a training environment rather than the final destination.

The framework assumes that:

Languages change.

Frameworks change.

Libraries change.

Engineering thinking remains valuable.

---

# 3. Definition of Competency

A competency is a repeatable engineering capability demonstrated across multiple contexts.

Competencies are not facts.

Competencies are not syntax.

Competencies represent reliable behaviors that improve software engineering performance.

Examples include:

- decomposing problems,
- designing algorithms,
- debugging systematically,
- communicating technical decisions.

---

---

# 5. Engineering Growth Principle

The objective is balanced development.

Exceptional engineers rarely excel because of one extraordinary skill.

They succeed because many competencies improve together.

For this reason, Blacksmith avoids maximizing one competency while neglecting others.

# Part 3 — Competency Progression Model

---

# 6. Purpose

Engineering competency develops gradually through repeated practice.

It cannot be accurately measured using a single exercise or one successful implementation.

The purpose of this progression model is to define how competency evolves and how Project Blacksmith determines readiness for increased difficulty.

Progression is based on demonstrated capability rather than time, effort, or completed lessons.

---

# 7. Universal Progression Model

Every competency inside Project Blacksmith follows the same progression.

```

```text
Level 0
Unaware

↓

Level 1
Exposure

↓

Level 2
Recognition

↓

Level 3
Application

↓

Level 4
Consistency

↓

Level 5
Mastery

↓

Level 6
Transfer
```

The student must demonstrate evidence before progressing.

Calendar time is never a progression criterion.

---

# 8. Level 0 — Unaware

Characteristics

- Has never encountered the concept.
- Cannot identify when it applies.
- Depends entirely on instruction.

Assistant Strategy

Introduce only the essential idea.

Avoid unnecessary complexity.

---

# 9. Level 1 — Exposure

Characteristics

- Has seen the concept.
- Can follow demonstrations.
- Frequently imitates examples.

Typical Behavior

"This looks familiar."

Mission Style

Highly guided.

Single objective.

Small scope.

---

# 10. Level 2 — Recognition

Characteristics

- Can identify situations where the concept applies.
- Still requires reminders.
- Begins forming mental models.

Typical Behavior

"I think this problem needs arrays."

Mission Style

Small variations.

Pattern recognition.

Comparison exercises.

---

# 11. Level 3 — Application

Characteristics

- Can independently solve familiar problems.
- Makes implementation mistakes.
- Requires review rather than instruction.

Typical Behavior

"I know what to do, but I made a mistake."

Mission Style

Real-world scenarios.

Limited guidance.

Multiple edge cases.

---

# 12. Level 4 — Consistency

Characteristics

- Produces reliable solutions repeatedly.
- Writes cleaner code.
- Tests more effectively.
- Explains decisions clearly.

Typical Behavior

"I've solved similar problems before."

Mission Style

Mixed challenges.

Integrated concepts.

Reduced hints.

---

# 13. Level 5 — Mastery

Characteristics

- Chooses appropriate solutions.
- Evaluates trade-offs.
- Reviews their own work critically.
- Adapts existing solutions.

Typical Behavior

"There are three possible approaches. Here's why I chose this one."

Mission Style

Projects.

Code reviews.

Refactoring.

Architecture discussions.

---

# 14. Level 6 — Transfer

Characteristics

- Applies knowledge to unfamiliar technologies.
- Learns frameworks quickly.
- Reads documentation independently.
- Builds solutions without tutorials.

Typical Behavior

"I've never used this library, but I understand the underlying pattern."

Mission Style

Unknown APIs.

New frameworks.

Real documentation.

Minimal guidance.

Transfer is the final objective of Project Blacksmith.

---

# 15. Progression Requirements

A competency advances only when the student consistently demonstrates:

✓ Correct reasoning.

✓ Correct implementation.

✓ Independent execution.

✓ Clear explanation.

✓ Reliable debugging.

✓ Appropriate testing.

One successful attempt is evidence.

Repeated success is progression.

---

# 16. Regression

Progress is not permanent.

If repeated weaknesses appear,

the competency may temporarily return to an earlier stage.

Regression is treated as:

Normal feedback,

not failure.

The objective is long-term stability.

---

# 17. Plateau Management

Learning often slows after rapid improvement.

When a plateau is detected,

Blacksmith may:

- introduce different problem contexts,
- assign debugging missions,
- increase explanation requirements,
- integrate project work,
- reduce hints.

The purpose is to stimulate new learning rather than simply increase difficulty.

---

# 18. Completion Statement

Competency progression measures engineering growth rather than topic completion.

Graduation from one level indicates that the student can repeatedly demonstrate engineering capability under different conditions, not merely reproduce a previously seen solution.

# Part 4 — Competency Assessment Framework

---

# 19. Purpose

The purpose of competency assessment is to measure engineering growth objectively.

Assessment should evaluate demonstrated capability rather than completed lessons or elapsed time.

A competency is considered reliable only when it is repeatedly demonstrated across different engineering contexts.

Assessment exists to improve learning—not to rank the student.

---

# 20. Assessment Principles

Every assessment follows five principles.

Principle 1

Assess behavior,

not memorization.

---

Principle 2

Assess reasoning,

not only correctness.

---

Principle 3

Assess consistency,

not isolated success.

---

Principle 4

Assess application,

not theoretical knowledge.

---

Principle 5

Assessment should always produce actionable feedback.

Every assessment should influence future missions.

---

# 21. Assessment Dimensions

Every competency is evaluated using the same dimensions.

Dimension 1

Understanding

Can the student explain the concept?

---

Dimension 2

---

Dimension 3

Can the student justify engineering decisions?

---

Dimension 4

Debugging

Can the student identify and fix mistakes?

---

Dimension 5

Adaptation

Can the student apply the competency in unfamiliar situations?

---

Dimension 6

Communication

Can the student explain the solution clearly?

These six dimensions create a complete engineering profile.

# 23. Observable Evidence

✓ Correct implementation.

✓ High-quality explanations.

✓ Well-designed test cases.

✓ Successful debugging.

✓ Appropriate trade-off discussions.

✓ Consistent project usage.

The assistant should avoid subjective judgments without supporting evidence.

# 26. Progression Rules

A competency progresses only when:

✓ Demonstrated repeatedly.

✓ Applied independently.

✓ Successfully used in different contexts.

✓ Explained correctly.

✓ Verified through review.

No competency progresses because of time alone.

---

# 27. Regression Rules

If repeated weaknesses appear,

the competency may temporarily decrease.

Regression is expected when:

- Long gaps without practice.
- Repeated misunderstanding.
- Heavy AI dependency.
- Inability to transfer knowledge.

Regression should trigger reinforcement,

not punishment.

---

Every future mission should answer three questions.

Question 1

Which competency is currently weakest?

Question 2

Which competency is required next by the curriculum?

---

Question 3

Can one mission improve both?

Whenever possible,

missions should strengthen multiple related competencies while maintaining one primary learning objective.

Competency assessment transforms Project Blacksmith from a collection of coding exercises into an adaptive engineering development system.

Every assessment should answer one question:

"Which engineering capability should improve next?"

# Part 5 — Competency Dependency Graph

---

# 31. Purpose

Engineering competencies do not develop independently.

Each competency depends upon one or more prerequisite competencies.

Understanding these relationships allows Project Blacksmith to diagnose root causes rather than symptoms.

The objective is to improve the weakest foundational competency instead of repeatedly treating visible failures.

---

# 32. Dependency Philosophy

A weakness observed during implementation is often caused by an earlier competency.

Example

Poor debugging

↓

Weak testing

↓

Poor decomposition

↓

Weak problem understanding

Improving debugging directly may produce only temporary improvement.

Improving decomposition strengthens every downstream competency.

# 35. Root Cause Analysis

For example:

Avoid architecture discussions if decomposition remains weak.

Avoid optimization if correctness has not yet been demonstrated.

Correct progression reduces unnecessary frustration.

↓

↓

Design maintainable solutions.

↓

Implement clean code.

↓

Test systematically.

↓

Debug methodically.

↓

Refactor confidently.

↓

Explain engineering decisions.

↓

Collaborate effectively with AI.

↓

Learn unfamiliar technologies independently.

---

# 46. Graduation Requirements

Graduation requires evidence across all competency domains.

The student must demonstrate:

✓ Independent problem solving.

✓ Professional code quality.

✓ Reliable debugging.

✓ Comprehensive testing.

✓ Clear technical communication.

✓ Sound engineering judgment.

✓ Successful project implementation.

✓ Technical interview readiness.

One exceptional project is insufficient.

Consistent performance across many engineering situations is required.

---

# 47. Graduate Behaviors

Graduates naturally demonstrate behaviors such as:

Thinking before coding.

Questioning assumptions.

Reading documentation independently.

Testing before asking for review.

Debugging systematically.

Considering trade-offs.

Seeking continuous improvement.

Helping other engineers.

These behaviors indicate engineering maturity.

---

# 48. Success Definition

Project Blacksmith succeeds when the graduate can:

Enter an unfamiliar codebase.

↓

Understand the architecture.

↓

Implement new functionality.

↓

Debug production issues.

↓

Review pull requests.

↓

Communicate technical decisions.

↓

Learn unfamiliar frameworks rapidly.

↓

Collaborate effectively with engineers and AI.

This represents professional engineering readiness.

---

# 49. Lifelong Learning

Graduation is not the end of learning.

It represents the beginning of independent engineering growth.

Graduates should possess the habits required to continue improving throughout their careers regardless of changes in languages, frameworks, tools, or AI capabilities.

---

# 50. Closing Statement

Project Blacksmith does not measure success by completed lessons, solved exercises, or memorized syntax.

Its measure of success is the development of engineers who think independently, build responsibly, communicate clearly, adapt continuously, and remain valuable in an AI-driven software industry.
