# Project Blacksmith
## Daily Mission Engine v1.0

---

# Purpose

Every day has exactly ONE primary mission.

The mission is designed to improve one or more engineering competencies.

The objective is NOT to finish quickly.

The objective is to improve thinking.

---

# Daily Mission Structure

Every mission follows the exact same structure.

Mission

↓

Objective

↓

Competencies Trained

↓

Prerequisites

↓

Problem Statement

↓

Constraints

↓

Deliverables

↓

Testing

↓

Interview Round

↓

Reflection

↓

Review

↓

Next Mission

---

# Mission Header

Every mission starts with:

Day Number

Mission Name

Difficulty

Estimated Time

Primary Competencies

Mission Type

Example:

Day 18

Mission Name:
Inventory Tracker

Difficulty:
Level 3

Estimated Time:
90 Minutes

Competencies:

- Problem Decomposition
- Arrays
- Objects
- State Management

Mission Type:

Build Mission

---

# Mission Types

A mission must belong to one primary category.

Logic

Build

Debug

Refactor

Optimization

Reading Code

Interview

Design

System Thinking

Projects

No two consecutive missions should be identical whenever possible.

---

# Mission Objectives

Every mission must define exactly ONE primary objective.

Bad Example

Learn Arrays, Objects, Loops, Functions

Good Example

Practice decomposing a real-world inventory problem using arrays.

---

# Problem Statement

The problem should simulate a real engineering task.

Avoid artificial textbook questions whenever possible.

The student should feel they are solving a meaningful problem.

---

# Constraints

Every mission includes engineering constraints.

Examples:

No AI for first 45 minutes

Maximum 3 functions

No loops

No Array methods

Memory limit

Performance requirement

Readable code required

Constraints force deeper thinking.

---

# Deliverables

Every mission requires:

Working Code

↓

Manual Test Cases

↓

Complexity Analysis

↓

Engineering Explanation

↓

Reflection

A mission without all five deliverables is incomplete.

---

# Testing

The student must create tests before requesting review.

Minimum:

Normal Cases

↓

Edge Cases

↓

Invalid Inputs

↓

Boundary Cases

---

# Interview Round

Every mission ends with interview questions.

Example:

Why did you choose this approach?

What are the trade-offs?

Can this be optimized?

What happens if the input doubles?

What assumptions did you make?

The objective is communication.

---

# Reflection

Every mission ends with:

What was difficult?

What mistake did I make?

What surprised me?

What would I improve?

Would I solve this differently tomorrow?

---

# Completion Criteria

A mission is complete only when:

Problem Solved

Tests Written

Code Reviewed

Interview Answered

Reflection Written

Git Commit Created

---

# Failure Policy

If the student cannot finish:

The mission is NOT skipped.

Instead:

Identify the obstacle.

Receive hints.

Retry.

Complete.

Learning is prioritized over speed.

---

# Adaptive Progression

The next mission depends on:

Current performance

↓

Repeated mistakes

↓

Review score

↓

Interview performance

↓

Confidence level

The curriculum adapts.

---

# Mission Quality Standard

Every mission must satisfy four questions.

1.

What engineering competency is trained?

2.

Where would a software engineer use this?

3.

How could this appear in an interview?

4.

How does this prepare the student for future missions?

If a mission cannot answer all four,

it must be redesigned.

---

# Final Principle

One mission.

One objective.

One measurable improvement.

Every day.

For ninety days.
