📄 02_Learning_Engine.md

Purpose: Define exactly how Project Blacksmith teaches, evaluates, adapts, and develops engineering thinking.

Project Blacksmith Learning Engine v1.0
1. Learning Philosophy

Project Blacksmith is not a teaching system.

It is an engineering training system.

The objective is not to transfer information.

The objective is to permanently improve the student's ability to think, solve problems, and build software.

Learning is measured through demonstrated ability, not exposure to information.

2. Core Learning Cycle

Every mission follows this cycle.

Problem

↓

Think

↓

Plan

↓

Code

↓

Test

↓

Debug

↓

Optimize

↓

Explain

↓

Reflect

↓

Feedback

↓

Next Mission

Skipping any stage weakens learning.

3. Active Learning Rule

Every concept must satisfy the following sequence:

Need

↓

Discover

↓

Understand

↓

Apply

↓

Repeat

↓

Master

The student should never read about a concept without immediately using it.

4. The 80/20 Rule

Time allocation for every mission.

Activity	Percentage
Thinking	20%
Coding	50%
Testing & Debugging	15%
Explanation & Reflection	15%

The program prioritizes implementation over passive study.

5. Mission Types

Project Blacksmith uses different mission categories.

Logic Mission

Objective:

Develop reasoning.

Build Mission

Objective:

Create working software.

Debug Mission

Objective:

Identify and fix problems.

Refactor Mission

Objective:

Improve code quality without changing functionality.

Interview Mission

Objective:

Practice explaining technical reasoning.

Reading Mission

Objective:

Understand unfamiliar code.

Optimization Mission

Objective:

Improve performance and scalability.

Design Mission

Objective:

Think before implementation.

7. Progression Rules

The student progresses only when:

Logic is correct.
Code is readable.
Edge cases are handled.
Solution can be explained.
Debugging is understood.

Simply reaching the correct output is insufficient.

8. Reflection Protocol

Every mission ends with five questions.

What was the hardest part?
What mistake did I make?
What did I learn?
What would I improve?
Could I solve this again tomorrow without help?

These answers become part of long-term learning.

9. Review Categories

Every solution is evaluated in:

Logic
Code Quality
Readability
JavaScript Knowledge
Edge Cases
Optimization
Debugging
Communication

Each category receives separate feedback.

10. Adaptive Learning

Future missions are determined by previous performance.

Examples:

If debugging is weak →

More debugging missions.

If explanations are weak →

Interview missions increase.

If arrays become easy →

Move to higher difficulty.

Weaknesses determine future training.

11. Long-Term Memory Rule

The program never assumes learning is permanent.

Concepts are intentionally revisited in new situations.

Example:

Arrays

↓

Objects

↓

Functions

↓

Project

↓

Interview

↓

Debugging

↓

Optimization

The same concept appears repeatedly in different contexts.

This develops flexible understanding instead of memorization.

12. Mastery Definition

A concept is considered mastered only if the student can:

Use it independently.
Explain it clearly.
Debug it.
Apply it in a project.
Recognize when it should not be used.
13. Failure Policy

Failure is expected.

Repeated failure without reflection is not.

Every mistake must produce learning.

14. Completion Criteria

A mission is complete only when all of the following exist:

Working solution.
Tested solution.
Explanation.
Reflection.
Git commit.
